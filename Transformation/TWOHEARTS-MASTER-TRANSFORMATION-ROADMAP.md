## Documentation and execution order

The first commit contains only this roadmap and the [progress tracker](TRANSFORMATION-PROGRESS.md). Verify the exact remote commit, both files, and the existing workflow on `master` before Stage 1. Conduct the full active source, route, asset, and evidence audit in Stage 1. Continue automatically after each verified checkpoint.

Each stage depends on the preceding stage's verified checkpoint and must meet its specific acceptance criteria and the shared checklist. The progress tracker records the status of all 23 stages. Each stage has its own `Transformation/Stage-N/REPORT.md`.

## Shared verification and Git checklist

Include this checklist in every stage report.

- [ ] Record the starting SHA, objectives, inspected files, initial behavior, decisions, changed files, visual and functional changes, dependencies, and stage-specific acceptance results.
- [ ] Run `./gradlew :app:testDebugUnitTest :app:assembleDebug`. Add focused regression or behavior tests for new or repaired functionality, run both unit-test variants at baseline and release, and run relevant instrumentation where Android is available.
- [ ] Render and inspect affected Jetpack Compose screens in light and dark, default and 200% font scale, narrow and standard widths, and a short viewport where applicable. Exercise empty, populated, long-content, error, and loading states with isolated test data. Require 48 dp interactive targets, 4.5:1 normal-text contrast, and usable controls without clipping or overlap. Compare composition, typography, surfaces, hierarchy, and motion with the approved visual identity. Refine weak results and rerender.
- [ ] Verify affected flows through production entry points. Check validation, save and retry behavior, navigation, restart, and retained data. Preserve the application ID, Room migration history, local files, and privacy boundaries.
- [ ] Record test and build results, visual evidence, Android device and API, known limitations, and the next stage. Run `git diff --check`, review the staged diff, commit independently, push, and verify the exact remote SHA and CI conclusion before advancing. Use a pull request if branch rules change. Use fast-forward pushes and preserve concurrent work.
- [ ] Update the progress tracker with completed stages, outstanding work, and the latest verified checkpoint. Record each stage's commit and CI result in its report and the tracker in the next documentation update, using the verified SHA from the published commit. Record the final exact SHA, workflow, artifact, and verification results in the delivery report.

Use `adb logcat -b crash` and `adb shell dumpsys activity exit-info com.twohearts.app` if a candidate launch fails or times out. If software emulation cannot provide reliable Android validation, use a supported hosted Android runner and record any remaining handset checks. An unresolved reproducible critical failure blocks advancement. Verify APK certificates before upgrade tests. A signing mismatch blocks an in-place upgrade claim. Preserve installed app data while resolving compatibility. The partial transfer covers only Notes and Reminders.

Reuse the existing schema and storage contracts where they meet requirements. Test any necessary migration against retained on-disk data before publishing. If the environment interrupts execution, record the stage, commit, evidence, blocker, and next task in the tracker.

Close the initiative after all 23 stages have documented results, every screen has passed the product audit, critical runtime issues are resolved, and GitHub Actions has produced the verified APK for the final `master` commit. The owner's confirmation covers the current baseline. The transformed APK's handset status remains pending until it is tested on the TECNO Spark 10 Pro.
