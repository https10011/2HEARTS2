‎TWOHEARTS VISUAL PRODUCTIZATION DIRECTIVE
‎
‎Document Type: Authoritative Visual/Product Direction
‎Status: DIRECTIVE — NOT A DEVELOPMENT PHASE
‎Applies To: Current V1 repository and all future visual/UX work
‎Priority: High
‎Product: TwoHearts
‎
‎---
‎
1. ‎PURPOSE OF THIS DOCUMENT
‎
‎This document records an important product-level direction for the
‎TwoHearts application.
‎
‎TwoHearts has already gone through extensive engineering,
‎UI/UX, design-system, motion, game, accessibility, performance,
‎and visual QA work.
‎
‎The application is functional and architecturally established.
‎
‎However, the current implementation has exposed a significant
‎presentation problem.
‎
‎Some screens and components technically exist and function
‎correctly, but visually they can still feel like:
‎
· ‎generic HTML/CSS interfaces
· ‎template-based application panels
· ‎collections of cards
· ‎minimally styled web components
· ‎a developer prototype rather than a finished product
‎
‎That is not the intended identity of TwoHearts.
‎
‎TwoHearts should ultimately feel like a real, standalone,
‎beautiful, emotionally warm couples application.
‎
‎This document establishes the visual direction required to close
‎that gap.
‎
‎---
‎
1. ‎THE CORE PROBLEM
‎
‎The problem is NOT primarily:
‎
· ‎architecture
· ‎database design
· ‎storage architecture
· ‎game-engine architecture
· ‎navigation architecture
· ‎backend architecture
· ‎security architecture
‎
‎The problem is primarily visual/product completeness.
‎
‎Examples of the current deficiencies that must be considered include:
‎
· ‎missing or insufficient logo presentation
· ‎generic-looking buttons
· ‎generic-looking cards
· ‎insufficient decorative identity
· ‎missing floral presentation
· ‎missing or underdeveloped avatar creation
· ‎missing or underdeveloped profile picture picker
· ‎insufficient profile personalization
· ‎weak onboarding visual identity
· ‎missing visual elements that existed in the original references
· ‎screens that technically work but do not feel emotionally designed
· ‎screens that look like HTML panels instead of an intentional mobile product
‎
‎These deficiencies should be treated as a visual productization
‎problem, not as evidence that the underlying application
‎architecture needs to be replaced.
‎

‎---
‎
1. ‎TWO VALID VISUAL STRATEGIES
‎
‎Future agents are explicitly allowed to use either of two
‎strategies depending on the quality and completeness of the
‎reference material.
‎
‎STRATEGY A — REFERENCE-LED
‎
‎When the reference screen provides strong visual direction:
‎
‎Use it as the foundation.
‎
‎Preserve its:
‎
· ‎visual hierarchy
· ‎color relationships
· ‎gradients
· ‎major composition
· ‎decorative elements
· ‎button concepts
· ‎floral concepts
· ‎relationship presentation
· ‎screen personality
‎
‎Then improve it with modern implementation quality:
‎
· ‎better spacing
· ‎better typography
· ‎stronger hierarchy
· ‎responsive behavior
· ‎better animations
· ‎better interaction feedback
· ‎accessibility
· ‎dark mode
· ‎text scaling
· ‎performance
‎
‎The reference establishes the direction.
‎
‎The implementation may improve the execution.
‎
‎---
‎
‎STRATEGY B — CREATIVE TWOHEARTS REDESIGN
‎
‎When a reference is incomplete, visually weak, unavailable, or
‎when the current implementation clearly feels like a generic
‎template, the agent is explicitly allowed to redesign the visual
‎presentation.
‎
‎The agent may use strong independent design judgment.
‎
‎The agent may:
‎
· ‎redesign layouts
· ‎improve backgrounds
· ‎introduce better gradients
· ‎improve card composition
· ‎redesign buttons
· ‎introduce richer visual hierarchy
· ‎improve onboarding
· ‎improve avatar presentation
· ‎improve profile creation
· ‎improve empty states
· ‎improve decorative composition
· ‎add tasteful illustrations
· ‎create more meaningful visual storytelling
· ‎add subtle atmospheric effects
· ‎create better game presentation
· ‎improve celebration states
· ‎create more sophisticated transitions
‎
‎However, creative freedom is subject to the non-negotiable
‎identity rules below.
‎
‎---
‎
1. ‎CREATIVE FREEDOM IS INTENTIONAL
‎
‎Future agents should NOT interpret the original PNG references as
‎a restriction preventing creativity.
‎
‎The purpose of the references is to establish the identity and
‎intent of TwoHearts.
‎
‎They are not intended to prevent improvement.
‎
‎If an agent can create a significantly more beautiful and
‎cohesive implementation while preserving TwoHearts identity,
‎that is encouraged.
‎
‎The desired result is not:
‎
‎«"The implementation looks exactly like the old PNG."»
‎
‎The desired result is:
‎
‎«"The implementation clearly belongs to TwoHearts and feels
‎better than the original reference."»
‎
‎---
‎
1. ‎NON-NEGOTIABLE BRAND IDENTITY
‎
‎The following rules MUST be preserved regardless of how creative
‎the visual redesign becomes.
‎
‎Official TwoHearts Logo
‎
‎The official TwoHearts logo must remain the official logo.
‎
‎Repository source:
‎
‎"TwoHearts-Logo-BrandName/"
‎
‎Do NOT:
‎
· ‎redesign the logo
· ‎replace the logo
· ‎generate a different logo
· ‎substitute plain text for the official logo
· ‎create duplicate logo implementations
‎
‎The centralized "BrandLogo" architecture established previously
‎should remain the authoritative mechanism for displaying the brand.
‎
‎---
‎
1. ‎BURGUNDY IS THE PRIMARY COLOR
‎
‎Burgundy should remain the dominant TwoHearts brand color.
‎
‎This does NOT mean every element should be burgundy.
‎
‎The agent may use complementary colors such as:
‎
· ‎warm cream
· ‎ivory
· ‎blush
· ‎dusty rose
· ‎muted pink
· ‎warm beige
· ‎plum
· ‎champagne/gold accents
· ‎deep burgundy
· ‎soft neutral colors
‎
‎Gradients are explicitly allowed.
‎
‎The overall result should remain recognizable as a
‎burgundy-first TwoHearts design.
‎
‎Avoid turning the application into an entirely different palette.
‎
‎---
‎
1. ‎ROSE AND LILY ARE CORE VISUAL ELEMENTS
‎
‎Rose and Lily are part of the emotional identity of TwoHearts.
‎
‎Repository source:
‎
‎"Rose Lily Vectors/"
‎
‎This directory contains the prepared Rose/Lily SVG assets.
‎
‎Future visual work should inspect and reuse these assets.
‎
‎The agent has creative freedom regarding:
‎
‎custom Generation of Rose Lily Svg assets or by getting them online on free sources if whats applicable and applying them on TwoHearts make sure the generated assets and etc are fit to be in TwoHearts
‎
· ‎size
· ‎placement
· ‎rotation
· ‎cropping
· ‎opacity
· ‎layering
· ‎pairing
· ‎background usage
· ‎foreground usage
· ‎section placement
· ‎animation
· ‎composition
‎
‎There is NO requirement that flowers appear in a fixed location.
‎
‎There is also NO requirement that flowers appear on every screen.
‎
‎In fact, excessive repetition should be avoided.
‎
‎Flowers should be used where they strengthen:
‎
· ‎romance
· ‎warmth
· ‎visual storytelling
· ‎hierarchy
· ‎emotional moments
· ‎onboarding
· ‎relationship screens
· ‎memories
· ‎timeline
· ‎milestones
· ‎empty states
· ‎celebrations
‎
‎The correct principle is:
‎
‎«Curated floral identity, not decorative clutter.»
‎

‎
‎The ultimate visual goal is NOT:
‎
‎«"A web application using burgundy CSS."»
‎
‎The goal is:
‎
‎«"A recognizable couples product called TwoHearts."»
‎
‎A person who sees the application for the first time should
‎immediately perceive:
‎
· ‎romance
· ‎intimacy
· ‎warmth
· ‎personalization
· ‎relationship
· ‎care
· ‎visual identity
‎
‎The application should feel intentionally designed rather than
‎assembled from generic components.

‎

‎not generic account settings.
‎
‎Where appropriate, the visual experience may include:
‎
· ‎framed avatars
· ‎decorative rings
· ‎subtle floral accents
· ‎warm gradients
· ‎personalized backgrounds
· ‎meaningful empty states
· ‎couple-oriented layouts
· ‎visual distinction between the two partners
‎
‎However, all existing storage and media architecture must be
‎preserved.
‎
‎Do not introduce external image hosting.
‎
‎Do not introduce cloud storage.
‎
‎Do not introduce remote profile-image services.

‎

‎
‎Buttons are a major part of perceived product quality.
‎
‎Future visual work should audit:
‎
· ‎primary buttons
· ‎secondary buttons
· ‎icon buttons
· ‎floating buttons
· ‎destructive buttons
· ‎navigation controls
· ‎game actions
· ‎dialog actions
‎
‎They should have coherent:
‎
· ‎shape
· ‎spacing
· ‎typography
· ‎icon placement
· ‎hierarchy
· ‎pressed state
· ‎disabled state
· ‎loading state
· ‎accessibility behavior
‎
‎Avoid generic browser-looking controls.
‎
‎---
‎
1. ‎CARDS MUST HAVE PERSONALITY
‎
‎Cards should not all feel like identical rectangles.
‎
‎Appropriate card types may have distinct personalities:
‎
· ‎relationship card
· ‎memory card
· ‎note card
· ‎reminder card
· ‎milestone card
· ‎game card
· ‎profile card
· ‎vault card
· ‎emotional empty-state card
‎
‎However, all cards must remain part of the same TwoHearts
‎visual language.
‎
‎Variation is encouraged.
‎
‎Visual chaos is not.
‎
‎---
‎
1. ‎BACKGROUNDS AND DEPTH
‎
‎Future visual work may introduce:
‎
· ‎warm gradients
· ‎radial lighting
· ‎subtle floral silhouettes
· ‎layered backgrounds
· ‎soft textures
· ‎atmospheric color
· ‎decorative SVG composition
· ‎subtle depth
‎
‎Avoid flatness where flatness makes the application feel like a
‎template.
‎
‎At the same time, backgrounds must never compete with primary
‎content.
‎

‎

‎
‎Reminders
‎
‎Gentle and organized.
‎
‎Places
‎
‎Adventurous and memory-oriented.
‎
‎Mood
‎
‎Expressive and emotionally warm.
‎

‎
‎Private, respectful, calm.
‎
‎Vault
‎
‎Secure, intimate, premium.
‎
‎Games
‎
‎Playful, energetic, interactive.
‎
‎Settings
‎
‎Calm, organized, trustworthy.
‎
‎Onboarding
‎
‎Memorable, welcoming, emotional.
‎
‎These are examples, not rigid templates.

‎
‎Animation is an important part of making the application feel
‎alive.
‎
‎The existing centralized Phase 25 motion architecture must remain
‎the foundation.
‎
‎Future animation may include:
‎
· ‎elegant screen transitions
· ‎gentle floral movement
· ‎card entrances
· ‎subtle button feedback
· ‎avatar reveal
· ‎selection feedback
· ‎save confirmation
· ‎relationship milestone celebration
· ‎game celebration
· ‎level-up moments
· ‎emotional empty-state entrances
‎
‎Animations should feel:
‎
· ‎smooth
· ‎intentional
· ‎warm
· ‎modern
· ‎responsive
‎
‎Avoid:
‎
· ‎excessive bouncing
· ‎constant movement
· ‎distracting effects
· ‎animation on every element
· ‎slow transitions
· ‎visual noise
‎
‎Reduced-motion behavior must always remain supported.
‎

‎
‎Do not create duplicate branding systems.
‎
‎Do not create duplicate floral systems.

1. ‎REFERENCE VS IMPLEMENTATION
‎
‎Future agents must distinguish between:
‎
‎PRODUCT REQUIREMENT
‎
‎What TwoHearts must do.
‎
‎VISUAL REFERENCE
‎
‎How the original design intended it to look.
‎
‎CURRENT IMPLEMENTATION
‎
‎What actually exists in the repository.
‎
‎A reference image should not be treated as a reason to destroy
‎working architecture.
‎
‎Likewise, existing code should not be treated as proof that the
‎visual experience is finished.
‎
‎All three must be considered together.

‎
‎Whenever visual work is performed, evaluate the result with this
‎question:
‎
‎«If someone who has never seen the source code opens TwoHearts,
‎does it look like a real standalone application?»
‎
‎Then ask:
‎
‎«Does it look intentionally branded?»
‎
‎Then:
‎
‎«Does it feel like a couples application?»
‎
‎Then:
‎
‎«Does it feel emotionally warm?»
‎
‎Then:
‎
‎«Does it feel polished enough that someone would want to keep
‎using it?»
‎
‎If the answer is no, the visual work is not finished.

1. ‎FINAL VISUAL STANDARD
‎
‎The ultimate standard for TwoHearts is not:
‎
‎«"All screens exist."»
‎
‎It is not:
‎
‎«"All tests pass."»
‎
‎It is not:
‎
‎«"The CSS has burgundy colors."»
‎
‎It is not:
‎
‎«"The application has animations."»
‎
‎The final standard is:
‎
‎«TwoHearts should look and feel like a deliberately designed,
‎emotionally warm, beautiful couples application with its own
‎recognizable identity.»
‎
‎The application should feel complete when someone opens it.
‎
‎The user should see:
‎
· ‎the TwoHearts identity
· ‎the burgundy visual language
· ‎tasteful Rose/Lily elements
· ‎beautiful relationship presentation
· ‎intentional buttons
· ‎intentional cards
· ‎meaningful typography
· ‎strong visual hierarchy
· ‎polished animations
· ‎personal profiles
· ‎thoughtful empty states
· ‎cohesive screens
· ‎a complete product experience
‎
‎rather than a collection of functional HTML/CSS panels.
