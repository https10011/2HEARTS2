# Local-first data & persistence foundation (Phase 2)

This document records the Phase 2 architectural decisions. The authoritative
specs (`MasterPrompt.txt`, `TwoHeartsRDMap.txt`) are unchanged.

## 1. Database choice — SQLite

**Decision:** SQLite is the single authoritative domain persistence layer.

- **Android:** `@capacitor-community/sqlite` (native bridge, Capacitor 6).
- **Browser/dev/tests:** `sql.js` (SQLite compiled to WASM), behind the same
  adapter interface — identical SQL, schema, migrations, and identifier
  strategy across contexts; the web dev build and APK never disagree about
  the schema.
- **Rejected:** IndexedDB (migrations/querying are primitive; weaker reports,
  harder joins — the relational roadmap: memories ↔ media, timeline filters,
  owner cross-references). localStorage beyond settings (640 KB-ish string
  only, no transactions). Dexie/PouchDB (IndexedDB wrappers — same argument,
  plus dependency bloat). Realm (heavy native dep; not Capacitor native).

Both engines run under ONE abstraction: `DatabaseAdapter`
(`src/data/database/adapter.ts`). Nothing outside `src/data/database` knows
which engine is active; `resolveDefaultAdapter()` in
`src/data/database/connection.ts` picks native on Android, sql.js otherwise.

Dependencies added (each justified — MasterPrompt §14 dependency discipline):

| Package | Reason |
|---|---|
| `@capacitor-community/sqlite` | Native SQLite for Android (primary engine) |
| `sql.js` | Same-API dev/web/test adapter; also serves CI/unit tests |
| `@types/sql.js` (dev) | Type bindings for sql.js |
| `@capacitor/filesystem` | Private app media storage on device |

No ORM; SQL is explicit because it is reviewable, testable, and the schema is
tiny. `google-services` stays an unapplied AGP classpath entry.

## 2. Layers

```
UI  →  State  →  Repository (src/repositories)  →  EntitySerializer
                                                   + Data access helpers
                                              →  DatabaseAdapter
                                              →  SQLite (native) | sql.js (web)

Media bytes:      UI  →  MediaStorage service  →  MediaFileSystem adapter
                                                 →  Capacitor Filesystem | Memory FS
Settings:         UI  →  appSettings (src/core)  →  SettingsStorage abstraction
                                                 →  localStorage (fallback: memory)
```

## 3. Domain model conventions (`src/data/model/entity.ts`)

Every persisted entity:

- `id: string` — **UUID v4**, lowercase hex; auto-increment row ids never leak
  into identity (sync-safe). Generated by `newId()` in `src/utils/ids.ts`
  (crypto.getRandomValues → Node test fallback). Validation helper `isValidId`
  rejects anything else — import/export validation and serializers use it.
- `createdAt / updatedAt: string` — ISO 8601 UTC (`YYYY-MM-DDTHH:mm:ss.sssZ`)
  via `src/utils/time.ts`. Injected `Clock` everywhere → deterministic tests.
  Lexicographic compare on this format = chronological compare (validated).
- `deletedAt: string | null` — optional tombstone. `TombstonedEntity` (e.g.
  media assets) sets it; repositories default-exclude tombstoned rows so a
  future V2 sync can propagate deletions. Enums are string unions; nullable
  uses `T | null` (serializers reject JSON blobs; no `any`).

## 4. Serialization (`src/data/serialization/entitySerializer.ts`)

One `EntitySerializer` per entity: constant column list, `toParams`,
`fromRow`. Date/boolean/enum/array rules are centralized: ISO strings for
dates, booleans as 0/1 via helpers, no `JSON.stringify` sprinkled in feature
code. `stableStringify` (sorted keys) exists for the export envelope where
deterministic output matters — it is not a storage format.

## 5. Initialization & lifecycle (`src/data/database/connection.ts`)

`initializeDatabase()` runs ONCE before the React tree mounts (`main.tsx`
renders an `AppGate`). Concurrent callers share one promise (no races); a
failure clears the memo → retry. `getDatabase()` throws
`PersistenceError('not-initialized')` for early access. `finalizeDatabaseForTests`
closes the engine cleanly. The APK ships the `sql-wasm` asset too, so the dev
build and native build stay compatible, but the resolver picks native when
Capacitor is present.

## 6. Schema versioning & migrations

- Current **schema version: 1** (single source: `src/config/persistence.ts`,
  asserted in tests against `ALL_MIGRATIONS`).
- `schema_migrations(id, name, applied_at)` records every applied migration.
- `runMigrations` filters applied, enforces strict ascending order, runs each
  migration in ONE transaction (no partial schema), and on failure reports
  `migration-failed` with what was already applied. Re-running migrations on
  an existing database is a no-op (idempotent — tested).
- New Phase N migrations append `00N_name.ts` side-by-side with the initial
  one and are picked up by `ALL_MIGRATIONS` (ascending).

## 7. Settings vs domain data

**Settings** (text size, onboarding, app-lock, UI prefs) live in `localStorage`
through `SettingsStorage` (`src/data/settings`) — NOT the domain DB. Rationale:
readable before DB init, tiny/flat, own schema version inside
`src/core/appSettings.ts` (which now routes through the abstraction; an
in-memory fallback protects devices where storage is denied). Feature/domain
code must never touch `localStorage` directly. **Domain data** (memories,
notes, …) lives solely in SQLite. If individual settings ever move into the
DB, it happens behind the same interface — never via ad-hoc engine calls.

## 8. Media storage (`src/data/media`)

- **Root**: `media/` inside the PRIVATE app directory
  (`@capacitor/filesystem` `Directory.Data`); browser/dev/tests use a memory
  driver for the `MediaFileSystem` interface.
- **Naming**: `media/{photos|videos}/{uuid}.{ext}` — generated IDs only, no
  user input on the path. `assertSafeRelativePath` rejects absolute paths,
  `..`, backslashes, and whitespace. UI receives `MediaReference
{id, kind, mimeType}` and resolves a `data:` URL via `MediaStorage.resolveUrl`
  — never a raw path (no traversal).
- **Metadata**: `media_assets(id, kind CHECK, mime_type, relative_path,
  size_bytes, created_at, updated_at, deleted_at)` — DB holds references,
  binaries stay on disk.
- **Lifecycle**: `store` runs the insert in a SQL transaction with a
  filesystem compensation action (rollback either way). `delete` tombstones
  the metadata then removes the file. `findOrphans`/`sweepOrphans` clean
  crash leftovers across `photos|videos` dirs.

## 9. Errors & transactions

`PersistenceError(code, message, {cause})` with codes:
`init-failed, not-initialized, migration-failed, query-failed,
transaction-failed, serialization-failed, media-fs-failed, media-missing`.
`normalizeError` wraps raw engine errors at the adapter boundary; only
predefined strings reach the UI/log surface via `safeMessageFor` — SQL text,
file paths, and domain values never leak (MasterPrompt §29 security). SQL
transactions are atomic (`BEGIN IMMEDIATE` … `COMMIT/ROLLBACK`),
single-migration-per-tx; multi-repository composition happens through
`DatabaseAdapter.transaction` (nested transactions are rejected loudly —
tests). Recovery: boot retry gate (`main.tsx`), sanitize → fallback, sweep.

## 10. Backup/export boundary (`src/services/backup`)

Envelope: `{ format: 'twohearts-export', formatVersion, exportedAt,
schemaVersion, entities: { mediaAssets, … } }`. Validation rejects unknown
formats/versions and *newer-than-local* schemas before any migration work —
the connector the import flow will use in a later phase. Media entries are
safe references; exporters package binaries alongside by reading through
`MediaStorage`. Backups stay local/user-controlled (roadmap entry points,
e.g. period data export, remain on-device).

## 11. Future V2 sync boundary

```
V1:  UI → State → Repository → Local Data Source
V2:  UI → State → Repository → Local Data Source → Optional Sync Layer
```

All sync prerequisites are already satisfied: UUID identity, ISO UTC
created/updated, tombstones on deletable entities, deterministic export
serialization, repository abstraction, local DB as source of truth. A future
sync adapter would sit BETWEEN repository consumers and remotes without
touching V1 boundaries (no V2 code exists in this phase).

## 12. Testing

Unit tests run on the real persistence stack (sql.js under Node 22's
`--experimental-transform-types` — no mocks): identifiers, timestamps,
serializers, migrations (ordering, idempotency, failure, version assert),
connection lifecycle, repository CRUD + tombstone semantics, settings
fallback, media store/resolve/delete/orphan sweep + fs rollback, transactions
& error normalization, export validation. The
native Capacitor engine is validated on-device at the APK integration level —
the adapter contract is identical (documented as NOT VERIFIED in unit tests).

## 13. Deferred

Camera/gallery plugins, packaging UX, period/games schemas, feature screens —
later phases, by spec order.
